# A. 嵌入式

## A1【重点】RS485 为什么用 DMA 双缓冲？原理是什么？

### A1.1 先看清约束（不看约束谈方案都是空的）

- UART7 跑 **4 Mbps**、8N1，半双工 RS485：MCU 发 16 B 命令，电机紧跟着回 16 B 反馈。
- 换算：10 bit/字节 → **2.5 µs/字节**；一帧 16 B 在线上 40 µs；一问一答 80 µs。
- 1 kHz 节拍里 `UnitreeMotor_Func()` 轮转发命令（2 台电机 → 每台 500 Hz）。
- 硬性要求：**一个字节都不能丢，也不能读到"写了一半"的缓冲**。

### A1.2 不用 DMA：逐字节中断为什么不行

- RXNE 中断频率 = 400 000 次/秒，平均每 2.5 µs 进一次中断。
- HAL 的中断入口 + 标志判断 + 回调 + 现场保存远不止 2.5 µs；只要有一次更高级中断/临界区超过 2.5 µs，下一个字节就到，触发 **ORE 溢出**丢字节。
- 丢 1 个字节 → 整帧 16 B 错位 → CRC 失败 → 这一拍反馈丢失。偶发、难复现，正是闭环控制最怕的故障形态。
- 结论：这个波特率下逐字节中断在工程上不可行。

### A1.3 只用 DMA 单缓冲：两种失效方式

- **覆盖撕裂**：CPU 正在处理 M0（搬运/校验），DMA 已经把下一批数据写进同一块 M0 → CPU 读到"半新半旧"的数据。
- **停机空窗**：为了不被覆盖，处理前先停 DMA、处理完再启动 → 停止的那段时间总线上的字节没人收。
  半双工下一问一答间隔只有几十 µs，这个空窗正好落在电机回包上 → 直接丢反馈。
- 另外还有一个次生问题：单缓冲要判断"这批收了多少字节"只能靠读 counter，处理完还要重装 counter，逻辑更容易出错。

### A1.4 双缓冲（DMA_DBM / ping-pong）原理

硬件把接收区拆成两块：M0 和 M1，由 `DMA_SxCR.CT` 指示"当前写入哪一块"。

```
时间 →
DMA(生产者):   [ 写 M0 ]            [ 写 M1 ]            [ 写 M0 ]
CPU(消费者):        [ 读 M0 ]            [ 读 M1 ]            [ 读 M0 ]
                     ↑ IDLE 触发          ↑ IDLE 触发          ↑ IDLE 触发
```

- DMA 永远在写"另一块"，CPU 永远在读"刚收满的那一块"，**读写物理隔离**，无需加锁，也不会读到写一半的数据。
- 双缓冲解决的不是"更快"，而是"**生产者与消费者的时间重叠**"：不需要为了处理而暂停接收。
- 本项目的触发不是"收满 64 B"，而是 **IDLE 空闲中断**（见 A1.5）：一帧 16 B 发完总线就会空闲 ~几十 µs，正好作为"这批数据到头了"的边界。

### A1.5 本项目代码里的完整时序

```
电机回包 16 B ──► DMA1_Stream2 写入当前目标缓冲(M0 或 M1)
                        │
                        ▼  总线空闲 → USART IDLE 中断
        HAL_UARTEx_RxEventCallback(huart7, Size)        IQRhandler.c:199
                        │
                        ▼
        UnitreeMotor_UART_RxHandler(...)                UnitreeMotor.c:352
          1. 读 CT：DMA 现在写的是哪块 → 那一块（当前目标）就是本次数据
          2. __HAL_DMA_DISABLE（ARM 要求 CT 只能在 EN=0 时改）
          3. 翻转 CT、重装 counter = 64、重新 enable
          4. SCB_InvalidateDCache_by_Addr(缓冲, Size)   ← D-Cache 一致性
          5. 逐字节推入环形缓冲 RingBuffer_Push
          6. UnitreeMotor_ParseRxQueue()：找 FD EE → 收满 16 B → CRC → 更新电机反馈
```

关键点逐条问自己：

- [ ] **为什么先读 CT 再翻转？** CT = 当前目标：CT=0 说明 DMA 正在写 M0，那么这批数据就在 M0，取 `src = M0`，然后把 CT 翻成 1，让下一批写 M1。`UnitreeMotor.c:364-377` 就是这个逻辑。
- [ ] **为什么改 CT 前要 disable？** 参考手册规定 CT 只能在流关闭（EN=0）时写；顺带把 counter 重装成 64，保证下一批的字节计数从 0 开始（HAL 用 `RxXferSize - counter` 算 Size）。
- [ ] **为什么还要 IDLE 中断？** DMA 只知道"搬够 64 B 了"，不知道"一帧结束了"。IDLE 提供帧/批次边界，把 16 B 的短帧变成一次可处理的完整批次。
- [ ] **为什么再加一层环形缓冲？** 把"字节流"和"帧"解耦：中断里只做搬运，帧同步/CRC/重同步交给解析器；坏帧、粘包、断帧都不会让接收停摆。
- [ ] **为什么缓冲要 `ALIGN_32B` 且放 `__RAM_D1_`？** 见 A5：D-Cache 维护按 32 B 行操作，对齐是防止 invalidate 波及同一行的邻居变量。

### A1.6 代价与已知风险（"会用"和"用对"的差距）

- **64 B 边界 case**：本实现默认"单次空闲批次 < 64 B"。若一批正好收满 64 B，硬件会在收满瞬间自动翻转 CT 并重装 counter；此时 HAL 在 CIRC 模式下仍按 IDLE 回调并把 Size 报成 64（`stm32h7xx_hal_uart.c:2425-2440`），而软件读到的是硬件翻转过的那一块（空/旧数据）→ 这一批真实数据被跳过，还可能往环形缓冲灌 64 B 垃圾。当前 16 B 帧不会触发，但要在注释里写明或加保护。
- **切换窗口**：IDLE 处理里 disable→切 CT→重装→enable 之间 DMA 不接收（几十个 CPU 周期），可接受但要知道。
- **中断里干活偏多**：逐字节 push + 解析 + CRC16 都在 `UART7` 中断里（优先级 5）。目前 1 ms 内 1~2 帧没压力；若以后总线负载上去，应改成"中断只搬运 + 任务里解析"。
- **它救不了方向切换的时序错误**：双缓冲保证"不丢字节"，但如果发送方向切太早/太晚（见 A2），照样截断或丢失。

## A2 RS485 半双工的方向控制："什么时候算发完了"

- 硬件：DE/RE 由 **PG1** 控制（`motor_config.h:66`，`gpio.c` 配成推挽输出），发送前 `Unitree_SetTxMode()`、发完 `Unitree_SetRxMode()`（`UnitreeMotor.c:61-91`）。
- 流程：置 TX → `HAL_UART_Transmit_DMA()` → **发送完成回调**里切回 RX（`UnitreeMotor.c:394-401`）。
- 核心知识点：**DMA 传输完成 ≠ 总线上发完**。DMA 完成只表示 16 B 都写进了 TDR，最后一个字节可能还在移位寄存器里。
- HAL 的处理：DMA Normal 模式下，DMA 完成后 HAL 使能 USART 的 TC 中断，真正的 `HAL_UART_TxCpltCallback` 是在 **TC（最后一位停止位移出）** 之后才回调的 → 在这个回调里切方向是安全的。若不经过 HAL、直接在 DMA 中断里切 DE，就会**截断最后一个字节**（表现为电机偶发 CRC 错/不响应）。

- [ ] 追问：为什么用 `uart->gState`（而不是 `RxState`）判断能不能发下一帧？（`UnitreeMotor.c:410` 附近：RX DMA 常开，RxState 一直是 BUSY）

## B1 "控制方式"地图：本项目选了哪一格

| 维度 | 选项 | 本项目 |
| --- | --- | --- |
| 空间 | 关节空间 / 笛卡尔空间 | **关节空间**（`ARM_*_POS` 是关节角，逆解函数被注释掉） |
| 轨迹 | 点到点 PTP / 连续轨迹 CP | **PTP**（每个点位单独走一段五次多项式） |

| 控制律 | 级联 PID / 计算力矩 / 阻抗导纳 | GO：`τ = kp·(q_d−q) + kd·(q̇_d−q̇) + τ_ff`（`q̇_d=0`、`τ_ff=0`） |

- 因此本项目的位置控制在"接触/碰撞"场景下是脆的：没有力感知、没有让位能力。这也是 C4 要补的。

## B2 关节空间 vs 笛卡尔空间

- 本项目 `User/src/kinematics.c` 有完整的平面 2R 正/逆解（余弦定理 + `atan2`，取肘上解），但实际运行走的是手调的关节角点位；`Arm_Interpolation_Pos_Start()` 被注释掉了（`seize_sky.c:122` 附近）。
- 关节空间 PTP 的优点：算得快、无奇异点问题、不依赖标定精度、调试直观（一个点位就是一串数）。

# C. 运动控制扩展（发散方向）

## C1 重力补偿：把 kp 从"扛重力"里解放出来

二自由度臂的重力力矩（m：质量，l：质心到关节距离，θ：几何角）：

```
τ1 ≈ [m1·g·l1 + m2·g·L1]·cos(θ1) + m2·g·l2·cos(θ1+θ2)
τ2 ≈ m2·g·l2·cos(θ1+θ2)
```
（θ 从水平方向起算，所以水平伸直时最大、竖直时为零；符号取决于关节正方向，上机前先用实测确认。）

- 把 τ 填进命令的 `torque`（前馈），位置环 kp 只负责"纠偏差"而不是"顶着整条臂"，跟随误差、发热、kp 都能降下来。
- 实验：静止时给不同 τ_ff，找出"kp 最小时仍能保持位置"的一组；再对比有无前馈时的误差曲线（VOFA+ 记录 cmd vs feedback）。

## C2 标定：几何 + 零位 + 传动

- 零位：多次回到同一机械基准取平均，消除回差与人为误差。
- 连杆长度：卷尺粗测 + 多组 (u1,u2) 点做最小二乘拟合。
- 传动比：命令电机转 N 圈（编码器值可读），量实际关节角，验证 5/6 与 6.33。
- [ ] 追问：零位误差是常数项、杆长误差是尺度项，它们在末端坐标上的表现分别是什么？哪个更容易被发现？

## C3 动力学与计算力矩控制

- 拉格朗日方程：`M(q)q̈ + C(q,q̇)q̇ + G(q) = τ`；二自由度臂可解析写出 M/C/G。
- 计算力矩（逆动力学）：`τ = M̂(q)·(q̈_d + Kd·ė + Kp·e) + Ĉ + Ĝ`，把非线性项前馈掉，让误差动力学变成线性二阶系统。
- 参数辨识：用已知轨迹采集 (q, q̇, q̈, τ)，最小二乘辨识质量/质心/惯量；只辨识 G 也已有明显收益。

## C4 阻抗/导纳：从"执行轨迹"到"会接触"

- 阻抗控制：把位置当软约束（现有 kp/kd 就是最简单的关节阻抗），接触时"让位"而不是死扛。
- 导纳控制：测力 → 修期望位置，适合放置、插拔、贴合。
- 竞赛场景：放块对孔、接触式定位、"推一下让它自己找正"。
- [ ] 追问：高 kp 纯位置控制撞到障碍时电流为什么飙升？为什么"软"一点反而更快完成任务？

## C5 振动抑制与平滑

- 长臂 + 轻结构 → 末端抖动；kp 调高会振，调低跟随差。
- 手段：输入整形（ZV/ZVD 脉冲序列抵消特定频率振荡）、更高阶轨迹（加 jerk 约束）、加速度限幅、陷波滤波 + IMU 反馈。
- 实验：同一条轨迹用五次多项式和梯形速度各跑一次，用加速度计/VOFA+ 对比末端振动。

## C6 感知闭环：视觉/传感器接入

- 时延问题：视觉 ~30 Hz、控制 1 kHz，视觉结果必须"预测 + 跟踪"，不能直接塞进 1 kHz 位置环。
- [ ] 追问：闭环里混入 100 ms 延迟会发生什么？为什么"先停到预对准点，再视觉修正"往往更稳？

## C7 通信与调度预算

- RS485：一帧 16 B ≈ 40 µs，一问一答 80 µs。2 台电机 @500 Hz = 80 ms/s ≈ **8% 总线占用**。
- 提到每台 1 kHz：≈16%，理论上可行，但要实测半双工转向 + 电机处理延时；6 台电机就接近 50%，需要重新设计调度。
- 时延链（当前）：1 ms 节拍 + 轮转最坏等 1 ms + 传输/解析 ≈ 2~4 ms 的等效滞后 → 这是 kp 不能无限加大的根因之一（相位裕度）。
- CAN：1 Mbps 标准帧约 110~130 bit ≈ 120 µs/帧，即每 1 ms 出队 1 帧 ≈ 12% 占用（每多一帧翻倍），还有余量。

- [ ] 追问：如果每台电机都要 1 kHz，轮转策略要改成什么样？（一次节拍发多台、按 ID 时间片、提高波特率、换全双工）

## C8 时间最优与比赛效率

- 联动 vs 顺序动作：末端扫掠体积、碰撞风险、对时间的敏感度不同；"转 2 → 转 1"能否改成并行+避障路径？
