# 诊断代码怎么写

现有工程已经接好了 VOFA 和 Event Recorder。使用现有六路波形及已有事件，不需要再写初始化或创建任务。下面的例子供以后修改通道、添加事件时参考，例子中的新通道和新事件没有自动加入运行代码。

## 先看代码分工

| 位置 | 做什么 |
|---|---|
| `Motor/src/UnitreeMotor.c` 的有效回包分支 | 校验通过后记录同一电机相邻回包的时间差 |
| `Motor/inc/UnitreeMotor.h` 的 `UnitreeLinkStats` | 保存最后有效回包时刻、计数和最近一次间隔 |
| `User/src/arm_diag.c` 的 `ArmDiag_Tick` | 每10 ms取快照并检查通信、到位和状态变化 |
| `ArmDiag_FillVofa` | 选择VOFA六个通道各放哪个变量 |
| `Application/src/myostasks.c` 的 `VOFA_SendTask` | 周期发送六路数据 |
| `ArmDiag_Record` / `ArmDiag_RecordSample` | 保存完整RAM快照，同时记录主事件；后者复用触发判断时的快照 |
| `ArmDiag_ExportDetails` | 异常、恢复或手动快照时，追加可随CSV保存的关键详细行 |
| `MDK-ARM/ArmDiagnostics.scvd` | 把事件编号和两个整数解释成可读文字 |

## VOFA：想看一个变量的连续变化

当前调用关系：

```text
freertos.c 创建 VOFA_SendTask
  → ArmDiag_FillVofa(channels) 选择六个数
  → VOFA_Channel_Update(...) 更新发送缓存
  → VOFA_Update() 经UART9发送JustFloat帧
```

例如 `ArmDiag_FillVofa` 默认分支里：

```c
channels[0] = sample.target[0];   // 电机0目标角，rad
channels[1] = sample.position[0]; // 电机0反馈角，rad
```

想把通道5改成通信是否正常，替换默认分支中对 `channels[5]` 的赋值：

```c
channels[5] = g_arm_comm_ok ? 1.0f : 0.0f;
// 1表示两台电机反馈都新鲜，0表示至少一台未上线/超时，或监测已关闭。
```

这样会替换原来的电机1力矩通道。当前发送库固定使用六通道，不要直接写 `channels[6]`，那会越界。把VOFA通道名改为“通信正常”，避免还显示成“力矩”。默认分支要求 `g_diag_vofa_profile=0`；1、2是单电机通道方案。

保存代码后F7编译，在允许重启且机械臂已安全停稳的条件下下载，再进入调试Run。VOFA继续使用UART9对应的COM、115200、8N1、JustFloat和显示间隔10 ms。当前六路数据没有真实逐帧时间戳，10 ms是显示换算间隔。

## Event Recorder：想记录某一件事发生了

现有工程在 `seize_sky.c` 启动时调用一次 `ArmDiag_Init()`，任务循环调用 `ArmDiag_Tick()`，开始与结束动作时分别调用 `ArmDiag_Start()`、`ArmDiag_End(...)`。因此已有事件会自动出现。

先练习一条现有事件：在Keil Watch把 `g_diag_capture_request` 改为1。机械臂任务会执行：

```c
ArmDiag_Record(ARM_EVT_MANUAL_SNAPSHOT, 0);
```

窗口出现 `ManualSnapshot`，随后是 `SnapshotContext` 及两台电机各自的 `SnapshotLink/Angles/Load`。这些行可以随事件窗口一起保存到CSV；相同seq表示同一份快照。完整RAM结构体不会自动展开，当前只导出主动选择的关键字段，详见[EventRecorder详细信息与导出](EventRecorder详细信息与导出.md)。

### 自己增加一个事件的三处修改

例如想在机械臂任务到达某个调试位置时记录一个标记：

1. 在 `arm_diag.h` 的 `ArmDiagEvent` 枚举末尾增加编号（21～26已由详细行占用，新事件从27开始）：

```c
ARM_EVT_DEBUG_MARK = 27
```

注意给前面的枚举项补逗号。

2. 在机械臂任务中需要记录的地方调用一次：

```c
ArmDiag_Record(ARM_EVT_DEBUG_MARK, 123U); // 123是自己定义的标记编号
```

在“刚进入某个步骤”或“条件从不成立变成成立”时调用。不要放在每次循环都会执行的位置，否则持续刷事件。`ArmDiag_Record` 的RAM队列按单个机械臂任务写入设计；其他任务要手动快照时可写 `g_diag_capture_request=1`，由机械臂任务处理。这个请求标志会合并同时发生的请求，并非多任务事件队列。

3. 在 `ArmDiagnostics.scvd` 的 `<events>` 内增加：

```xml
<event id="0x301B" level="Op" property="DebugMark"
       value="state=%d[val1], marker=%d[val2]"/>
```

`0x30`是组件号，`0x1B`是十进制27；`val1`是函数自动传入的动作状态，`val2`是上面传入的123。重新编译下载C代码；SCVD修改后在合适时机重新进入调试让Keil加载。原来添加的同一路径SCVD无需重复添加。

新增枚举和SCVD只定义显示方式，真正的检测条件、何时调用仍由C代码决定。Event Recorder也不会因为某事件显示红色就自动停止电机。

## 我增加的部分与现有工具的关系

VOFA负责传输和画波形，Event Recorder负责记录和显示事件；回包新鲜度、动作结果、故障边沿检测、16条RAM环形记录和首次故障快照是本工程增加的逻辑。日常只看 `g_arm_comm_ok` 和事件记录，需要定位问题时再展开快照。

第四次测试后已删除P50/P95、256样本窗口和直方图计算。10 ms通信超时阈值保持不变，判断仍使用最后有效反馈到现在的年龄。可选的 `Unitree_link[i].last_gap_ms` 只在新有效回包时更新，断线期间会保留旧值，因此不用于判断当前是否在线。
