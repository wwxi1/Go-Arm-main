# 轨迹规划与笛卡尔空间改造指南

对象工程：`Go-Arm-main`（新版）
涉及文件：`User/src/seize_sky.c`、`User/inc/seize_sky.h`、`User/src/kinematics.c`、`User/inc/kinematics.h`

---

## 0. 一句话总览

| 概念 | 方向 | 输入 → 输出 | 干什么 |
|------|------|------------|--------|
| 正运动学 `Forward` | 由内向外 | 电机角 (u1, u2) → 末端 (x, y) | 看"现在末端在哪" |
| 逆运动学 `Inverse` | 由外向内 | 末端 (x, y) → 电机角 (u1, u2) | 算"要去 (x,y) 该怎么转" |
| 轨迹规划 | 沿时间 | 起点 + 终点 + 时长 → 一串中间点 | 决定"怎么走过去" |

你现在的组合是 **轨迹规划（关节角空间）**，正逆解目前只用于调试监控。
要升级成 **笛卡尔空间轨迹规划**，就是把"插值对象"从关节角换成末端坐标。

## 1. 五次多项式：从需求到系数

### 1.1 为什么要有 `s`

电机从 A 走到 B，不能瞬移。用比例描述当前位置：

```
当前位置 = 起点 + (终点 − 起点) × s
```

`s` = "已经走了百分之多少"，0 = 在起点，1 = 到终点。
核心问题：**s 随时间 t 怎么变？**

`s` 必须与行程、时长无关，才能一段代码通吃所有运动。所以先把时间归一化：

```
t = time / total_time      t ∈ [0, 1]     归一化进度（不是秒）
s = f(t)                   s ∈ [0, 1]     已完成比例
```

### 1.2 为什么不能用线性 `s = t`

线性意味着匀速 → **起点速度从 0 瞬跳到 1，终点从 1 瞬跳回 0**。
速度突变 = 加速度无穷大 = 无穷大的力。物理上是齿轮咯噔、电机嗡鸣、结构抖动。

所以要控制的不只是位置，还有**速度、加速度**。

### 1.3 六条要求 → 六个方程

| 条件 | 数学表达 | 含义 |
|------|---------|------|
| 从起点出发 | s(0) = 0 | 不允许一开始就偏移 |
| 走到终点 | s(1) = 1 | 必须走满 |
| 起步速度 | s′(0) = v0 | 可配，当前 0.8 |
| 到点速度 | s′(1) = 0 | 不撞 |
| 起步加速度 | s″(0) = acc0 | 可配，当前 4.6 |
| 到点加速度 | s″(1) = 0 | 不抖 |

### 1.4 为什么是"五次"

选择 `s(t) = a1t + a2t² + a3t³ + a4t⁴ + a5t⁵`（常数项 a0 被 `s(0)=0` 消掉）。

- 3 次多项式只有 4 个系数 → 最多满足 4 个条件，管不到加速度
- **项数由条件数决定**：要把加速度也管住，就必须有 5 次项

"高次幂"的作用就是——**给那些额外边界条件准备的可调旋钮**。

### 1.5 3/4/5 和 6/12/20 从哪来

求导把指数拉到前面当系数：

| 项 | s(t) | s′(t) | s″(t) |
|----|------|-------|-------|
| a3t³ | a3t³ | **3**a3t² | **6**a3t |
| a4t⁴ | a4t⁴ | **4**a4t³ | **12**a4t² |
| a5t⁵ | a5t⁵ | **5**a5t⁴ | **20**a5t³ |

令 t = 1，剩下三行方程（`v0 = acc0 = 0` 的简化版）：

```
(1) a3 +  a4 +  a5 = 1      ← s(1) = 1
(2) 3a3 + 4a4 + 5a5 = 0      ← s′(1) = 0
(3) 6a3 + 12a4 + 20a5 = 0    ← s″(1) = 0
```

### 1.6 消元手算（10 / −15 / 6 的由来）

```
(2) − 3×(1):  a4 + 2a5 = −3                      消掉 a3
(3) − 2×(2):  4a4 + 10a5 = 0  →  2a4 + 5a5 = 0    消掉 a3
```

由 `a4 = −3 − 2a5` 代入 `2a4 + 5a5 = 0`：

```
2(−3 − 2a5) + 5a5 = 0
−6 − 4a5 + 5a5 = 0
a5 = 6
```

回代：`a4 = −3 − 2×6 = −15`，`a3 = 1 − (−15) − 6 = 10`。

### 1.7 一般情况（带 v0、acc0）

| 系数 | 全零版 | 代码里的写法 |
|------|--------|-------------|
| a1 | 0 | `v0` |
| a2 | 0 | `acc0 / 2` |
| a3 | 10 | `10 − 6v0 − 1.5acc0` |
| a4 | −15 | `−15 + 8v0 + 1.5acc0` |
| a5 | 6 | `6 − 3v0 − 0.5acc0` |

把 `v0 = acc0 = 0` 代入右列 → 落回左列，说明一般式正确。

**代入当前配置** `v0 = 0.8, acc0 = 4.6`：

```
a1 = 0.8
a2 = 2.3
a3 = 10 − 4.8 − 6.9  = −1.7
a4 = −15 + 6.4 + 6.9 = −1.7
a5 = 6 − 2.4 − 2.3   =  1.3
```

对应 `seize_sky.c:97-101` 那五行——**不是魔法数字，是上面三行方程解出来的结果**。

### 1.8 当前配置 vs 全归零的实测对比

| 指标 | v0=0.8, acc0=4.6 | 全归零 |
|------|------------------|--------|
| 起步速度 s′(0) | 0.8 | 0 |
| 起步加速度 s″(0) | 4.6 | 0 |
| 峰值速度 | 1.595 @ t = 0.33 | 1.875 @ t = 0.50 |
| 峰值 \|加速度\| | 4.60 @ t = 0 | 5.77 @ t = 0.21 |
| 运动节奏 | 偏前（前 1/3 冲峰值） | 正中对称 |

结论：当前配置**峰值更低**，但**起点有阶跃、节奏偏前**。真实物理量要乘回行程：

```
实际起步速度   = Δθ × v0 / T
实际起步加速度 = Δθ × acc0 / T²
```

`v0/acc0` 是全局常量，不随行程缩放 —— **行程越大越需要注意**（如 `SKY → KEEP` 的 Δdj = 65°）。

## 2. running / finish 守卫机制

所有 `Arm_*_Process()` 里都有同一个守卫：

```c
if (ArmControl.running == false && ArmControl.finish == false)
    Arm_Interpolation_Start(...);
```

它是一把**一次性锁**，四种取值组合里只有一格放行：

| 阶段 | running | finish | 守卫 | 谁把标志改成这样 |
|------|---------|--------|------|-----------------|
| ① 上电初始化 | 0 | 1 | 挡住 | `Arm_Control_Init` 故意置 `finish = true` |
| ② 状态变化 | 0 | 0 | **放行** | `Arm_Control_Task:561-566` 换挡重置 |
| ③ 轨迹运行中 | 1 | 0 | 挡住 | `Arm_Interpolation_Start` |
| ④ 轨迹到点 | 0 | 1 | 挡住 | `Arm_Interpolation_Update` 收尾 |

**效果**：每个状态变化恰好触发一段轨迹，不多不少。① 置 `finish = true` 是防止上电后立刻乱动。

`Arm_Interpolation_Update` 里被注释的 `// Is_pick=0; ...` **不是 bug** —— 这些标志在 `Arm_State_Update`（TIM2 中断里）每个分支末尾都被无条件清掉了，等轨迹跑完早就清干净了。

## 3. 关节空间 vs 笛卡尔空间

### 3.1 区别在哪

| | 关节空间（当前） | 笛卡尔空间 |
|---|---|---|
| 插值对象 | u1、u2、dj 三个电机角 | 末端坐标 (x, y) + dj |
| 逆解调用次数 | 起点一次（或零次） | **每 1ms 一次** |
| 末端轨迹 | 弓形弧线 | 直线 |
| 末端速度 | 时快时慢、方向不定 | 均匀可控 |
| 计算量 | 极小 | (sqrt + acos + 2×atan2) × 1kHz |
| 填表内容 | 电机角（需要试出来的数字） | 坐标（可以用尺子量出来的 mm） |

### 3.2 笛卡尔空间的好处

1. **末端走直线** —— 插块、穿过窄口、贴壁运动时才可控
2. **末端速度可控** —— 关节角匀速 ≠ 末端匀速；抓放时末端速度均匀才稳
3. **点位可测量** —— 直接用卷尺量出 mm 坐标填表，不用反复试电机角
4. **换机构不用重填表** —— 改臂长 L1/L2 即可，坐标表不动
5. **避障更容易** —— 可以在笛卡尔空间检查路径是否碰到障碍

### 3.3 代价与风险

| 风险 | 说明 | 对策 |
|------|------|------|
| 奇异位形 | 手全伸（`\|cosθ2\| → 1`）时，位置微调导致 θ1 剧变 | 路径避开、或末端限速 |
| 逆解不唯一 | 同一个点有两个姿态（肘上/肘下） | 现在是 `θ2 = +acosf()` 固定取肘上，要确认这是机构能到的那一支 |
| 超可达域静默失败 | `kinematics.c:69-70` 只把 cos 夹紧到 [−1,1]，**不报错** | 先算 `r = √(x²+y²)`，`r > L1+L2` 或 `r < \|L1−L2\|` 时拒绝执行 |
| 计算量 | 每周期一次 `Inverse` | M7 硬件 FPU + 现有代码已在任务里跑 Forward+Inverse（`seize_sky.c:554-560`），1kHz 下占用可忽略 |

## 4. 怎么启用坐标模式

> **先分清一件事**：被注释掉的 `Arm_Interpolation_Pos_Start`（`seize_sky.c:127-137`）**不是**"笛卡尔直线插补"，它是路线 A —— 只把"输入端从关节角换成了坐标"，插补仍在关节角空间做，**末端照样走弧线**。
>
> 两者的唯一实质差异是**逆解被调用的次数**：路线 A 整个运动只调 1 次（Start 时），路线 B 每 1 ms 调 1 次（Update 里）。想让末端真的走直线，**必须改 `Arm_Interpolation_Update`**，光解注释没用。

### 4.0 前提：先把 `Target_Quintic_Interpolation` 拆开

现在它把"算 s"和"应用 s"混在一起了。笛卡尔模式下需要**单独的 s**：

```c
// 只算归一化进度 s
static float Quintic_S(float time, float total_time)
{
    float t, t2, t3, t4, t5;
    const float v0   = ARM_START_VELOCITY;
    const float acc0 = ARM_START_ACCEL;

    if (total_time <= 0.0f) return 1.0f;

    t = time / total_time;
    if (t <= 0.0f)      t = 0.0f;
    else if (t >= 1.0f) t = 1.0f;

    t2 = t * t;  t3 = t2 * t;  t4 = t3 * t;  t5 = t4 * t;

    return v0 * t
         + 0.5f * acc0 * t2
         + (10.0f - 6.0f * v0 - 1.5f * acc0) * t3
         + (-15.0f + 8.0f * v0 + 1.5f * acc0) * t4
         + (6.0f - 3.0f * v0 - 0.5f * acc0) * t5;
}

// 原有接口保持不变，内部复用
static float Target_Quintic_Interpolation(float start_angle, float target,
                                          float time, float total_time)
{
    float s = Quintic_S(time, total_time);
    return start_angle + (target - start_angle) * s;
}
```

**这一步是纯重构，不改变任何现有行为**，可以先单独合入验证。

### 4.1 路线 A：最小改动（只保证终点正确）

直接把 `seize_sky.c:127-137` 那段注释解掉即可 —— **但要注意：这条路走不出直线，它只是"用坐标填目标"的入口。** 函数体本身是对的：

```c
static void Arm_Interpolation_Pos_Start(float pos_x, float pos_y,
                                        float dj_target, float move_time)
{
    Vec2 Pos_target;
    Pos_target.x = pos_x;
    Pos_target.y = pos_y;

    Unitree_Theta_t angle_target = Inverse(Pos_target);

    Arm_Interpolation_Start(angle_target.u1_theta, angle_target.u2_theta,
                            dj_target, move_time);
}
```

- **优点**：改动量 = 删注释；五轴同步逻辑不变
- **缺点**：`Inverse` 只在起点算一次，之后 1 秒里仍在关节角空间插值 → **末端走弧线**，不是直线
- **适用**：抓放块这种"只关心终点、不关心中间路径"的场景

> 注意命名：`Inverse` 返回的 `u1_theta / u2_theta` 名字带 theta，但内容已经是**电机角**（`kinematics.c:79-80` 已经调过 `Geom2Motor`）。传进 `Arm_Interpolation_Start` 是对的，只是名字容易看错。

### 4.2 路线 B：真笛卡尔插值（末端走直线）

**第 1 步**：在 `ArmControl_t`（`seize_sky.h:115-135`）里加一段笛卡尔状态：

```c
typedef struct
{
    float start_x;
    float start_y;
    float target_x;
    float target_y;
    bool  cartesian;      // true = 本段走笛卡尔模式
} ArmCart_t;
```

在 `ArmControl_t` 中加成员：`ArmCart_t cart;`

**第 2 步**：新增笛卡尔专用启动函数。**起点不要用目标反推，要用当前实际电机角正推**：

```c
static void Arm_Interpolation_Cart_Start(float pos_x, float pos_y,
                                         float dj_target, float move_time)
{
    Unitree_Theta_t now;
    now.u1_theta = Unitree_motors[0].data.position;
    now.u2_theta = Unitree_motors[1].data.position;

    Vec2 now_pos = Forward(now);        // 起点 = 此刻真实末端位置

    ArmControl.cart.start_x  = now_pos.x;
    ArmControl.cart.start_y  = now_pos.y;
    ArmControl.cart.target_x = pos_x;
    ArmControl.cart.target_y = pos_y;
    ArmControl.cart.cartesian = true;

    ArmControl.dj.start_angle = DJmotor[0].valNow.angle_deg;
    ArmControl.dj.target      = dj_target;

    ArmControl.time       = 0.0f;
    ArmControl.total_time = move_time;
    ArmControl.running    = true;
    ArmControl.finish     = false;
}
```

**第 3 步**：改 `Arm_Interpolation_Update`，加一个笛卡尔分支：

```c
static void Arm_Interpolation_Update(void)
{
    if (ArmControl.running == false) return;

    float s = Quintic_S(ArmControl.time, ArmControl.total_time);

    if (ArmControl.cart.cartesian)
    {
        // 1) 笛卡尔空间插值出本周期目标点
        Vec2 p;
        p.x = ArmControl.cart.start_x
            + (ArmControl.cart.target_x - ArmControl.cart.start_x) * s;
        p.y = ArmControl.cart.start_y
            + (ArmControl.cart.target_y - ArmControl.cart.start_y) * s;

        // 2) 可达域检查（现在 Inverse 是静默夹紧，不报错，必须自己查）
        float r = sqrtf(p.x * p.x + p.y * p.y);
        if (r > (ARM_U1_LENTH + ARM_U2_LENTH) ||
            r < fabsf(ARM_U1_LENTH - ARM_U2_LENTH))
        {
            ArmControl.running = false;
            ArmControl.finish  = true;
            return;                      // 超域：停止本段，不要下发错误角度
        }

        // 3) 每周期解一次逆解，当"翻译层"用
        Unitree_Theta_t th = Inverse(p);
        Unitree_motors[0].cmd.position = th.u1_theta;
        Unitree_motors[1].cmd.position = th.u2_theta;

        // 4) DJ 大关节不在平面臂里，仍走关节空间
        DJmotor[0].valSet.angle_deg = ArmControl.dj.start_angle
            + (ArmControl.dj.target - ArmControl.dj.start_angle) * s;
    }
    else
    {
        // 原有关节空间分支，保持不变
        Unitree_motors[0].cmd.position = Target_Quintic_Interpolation(
            ArmControl.u1.start_angle, ArmControl.u1.target,
            ArmControl.time, ArmControl.total_time);
        Unitree_motors[1].cmd.position = Target_Quintic_Interpolation(
            ArmControl.u2.start_angle, ArmControl.u2.target,
            ArmControl.time, ArmControl.total_time);
        DJmotor[0].valSet.angle_deg = Target_Quintic_Interpolation(
            ArmControl.dj.start_angle, ArmControl.dj.target,
            ArmControl.time, ArmControl.total_time);
    }

    ArmControl.time += ARM_INTERPOLATION_DT;

    if (ArmControl.time >= ArmControl.total_time)
    {
        ArmControl.time = ArmControl.total_time;

        if (ArmControl.cart.cartesian)
        {
            // ⚠️ 终点是"坐标"，不能直接赋给 cmd.position（量纲不同），必须再解一次逆解
            Vec2 p_end;
            p_end.x = ArmControl.cart.target_x;
            p_end.y = ArmControl.cart.target_y;
            Unitree_Theta_t last = Inverse(p_end);
            Unitree_motors[0].cmd.position = last.u1_theta;
            Unitree_motors[1].cmd.position = last.u2_theta;
        }
        else
        {
            Unitree_motors[0].cmd.position = ArmControl.u1.target;
            Unitree_motors[1].cmd.position = ArmControl.u2.target;
        }

        DJmotor[0].valSet.angle_deg = ArmControl.dj.target;
        ArmControl.running = false;
        ArmControl.finish  = true;
    }
}
```

> **为什么收尾要单写一遍**：`s` 在 `t = 1` 时精确等于 1，理论上 `Inverse(目标坐标)` 和插补出来的最后一个点是一样的。但 `ArmControl.time` 是浮点累加的（`+= 0.001f`），最后一拍很可能落在 `t = 0.999` 而不是 `1.0`，此时若靠插补值收尾，末端会**永久停在离目标几个微米到零点几毫米的位置**。所以到点后必须显式"钉死"到目标——关节模式钉角度，笛卡尔模式钉坐标再解一次。
>
> **最容易写错的一处**：坐标模式和角度模式的量纲完全不同，笛卡尔分支的收尾千万不能写成 `cmd.position = ArmControl.cart.target_x`。

**第 4 步**：把 `Arm_Position_Process()`（`seize_sky.c:360-368`）里现在写死的 KEEP 常量换成真正的坐标入口：

```c
static void Arm_Position_Process(void)
{
    if (ArmControl.running == false && ArmControl.finish == false)
    {
        Arm_Interpolation_Cart_Start(Target_Vec.x, Target_Vec.y,
                                     ARM_DJ_KEEP_POS, ARM_MOVE_TIME);
    }
}
```

`Target_Vec` 已经在 `seize_sky.c:31` 声明好了，正好派上用场（可以用 FDCAN 接收（x, y）来设置它）。

| | 路线 A | 路线 B |

| 改动量 | 删注释 | 改 3 个函数 + 加结构体成员 |

## 5. 启用前的检查清单

### 5.0 坐标系定义（先看这个，不然 5.1 的标定无从下手）

**代码里只有 x、y 两个分量，没有 z。** `kinematics.h:18-22` 定义的是 `Vec2 { float x, y; }`，`Forward`/`Inverse` 全程只处理这两维。`Algorithm/inc/vector.h` 里的 `Vec3d` 是通用数学库残留，机械臂链路未使用。

| 项 | 结论 | 依据 |
|----|------|------|
| 是哪个坐标系 | **固定在肩关节上的臂平面 2D 右手系**（非场地系、非底盘系） | `kinematics.c:52-53` 只有两根连杆向量求和，无任何常数偏移项 |
| 原点 | **u1/u2 同轴转轴（肩关节）中心** | 同上，无偏移项 ⇒ 原点就是大臂起点 |
| +x 方向 | **θ1 = 0 的方向**，即 `u1 = 0` 时大臂的指向 | `kinematics.c:14` 注明 θ1 为"大臂与 +x 轴夹角"；`ARM_U1_ZERO_POS = 0.0f`（占位值）⇒ θ1 = u1 |
| +y 方向 | **+x 逆时针 90°**（标准数学右手系：x=L·cosθ、y=L·sinθ） | `kinematics.c:52-53` |
| 单位 | x、y 为 **mm**；`u1`/`u2` 为 **rad**；`dj` 为 **deg** | `kinematics.h:17` |

符号方向（对实操最关键）：

| 量 | 增大的物理效果 | 偏导 |
|----|---------------|------|
| `u1` ↑ | θ1 增大 → 大臂朝 **+y 侧（逆时针）**转 | ∂θ1/∂u1 = +1 |
| `u2` ↑ | θ2 减小 → 肘关节变小（小臂相对大臂**伸直**） | ∂θ2/∂u2 = −2/3 |
| `dj` ↑ | 与 (x, y) 无关，纯独立自由度 | 无耦合 |

**θ2 的物理含义**：θ2 = 0 表示大臂小臂共线（完全伸直），θ2 越大肘部弯得越厉害。

#### 标定四步（求 Z1、Z2、RATIO）

| 步骤 | 操作 | 得到 |
|------|------|------|
| ① 定 +x | 选一个可反复复现的物理方向（推荐"大臂水平、指向场地"） | — |
| ② 求 `Z1` | 大臂摆到与 +x 重合、小臂与之共线，读 `u1` | `Z1 = −u1`（使 θ1 = 0） |
| ③ 求 `Z2` | 保持肘部伸直（θ2 = 0），读 `u1`、`u2` | `Z2 = (u1 + u2) × RATIO` |
| ④ 求 `RATIO` | 摆两个不同肘角，各读一次 `u1`、`u2` | `RATIO = Δθ2 / Δ(u1 + u2)` |

#### dj 与"场地坐标"的关系（为什么代码里没有 z）

若 `dj` 是**底座/腰部回转**，它才是几何上的"绕 z 轴旋转"，此时真正的场地坐标需要多做一次旋转：

```c
float dj_rad = DJmotor[0].valNow.angle_deg * 3.14159265f / 180.0f;  // dj 单位是度
world_x = x * cosf(dj_rad) - y * sinf(dj_rad);
world_y = x * sinf(dj_rad) + y * cosf(dj_rad);
```

**代码从未做这一步。** 因此同一个 `(x, y)` 在不同 `dj` 下对应场地里的不同物理位置——`(x, y)` 永远只是"臂平面内"的坐标。

若 `dj` 其实是**腕部回转**，它只改变夹爪朝向、不改变末端位置，更不该参与 (x, y) 换算。

**区分方法**：转 `dj` 时观察夹爪——绕肩关节画圆 ⇒ 底座回转（z 轴）；原地只转朝向 ⇒ 腕部回转。

### 5.3 ⚠️ 用实测验证 `(u1 + u2)` 这个符号

代码里 `kinematics.c:30` 写的是：

```c
return ARM_U2_ZERO_POS - (u1 + u2) * ARM_U2_RATIO;
```

而 `kinematics.h:14` 注释写的是"`(大臂电机角 − 小臂电机角) × RATIO`"。**注释和代码不一致。**

更关键的是物理一致性：如果 θ2 真是 `−(u1+u2)` 的形式，那么 u1、u2 **同向同步各转 Δ** 时，θ2 会变化 `−2RΔ ≠ 0`。
但机械上大臂转动会**带动**小臂电机同步转，此时肘关节角应该**不变**。这两个说法只有在"u2 读数与转动方向相反"时才自洽。

**验证方法**（5 分钟就能定论）：
1. 上电使能，记下当前 u1、u2
2. 手动把大臂摆约 10°，小臂电机不主动给指令
3. 读新的 u1、u2，看变化量是同号（`+Δ, +Δ`）还是反号（`+Δ, −Δ`）

**预期结果：反号（Δu2 = −Δu1）。** 推导如下——物理上大臂刚性摆动时肘关节角必须不变，即要求 ∂θ2/∂u1 = 0；按代码的 `θ2 = Z2 − (u1+u2)·R`，该条件等价于 Δu2 = −Δu1。

- 实测**反号** ⇒ 代码的 `+` 是对的，`kinematics.h:14` 的 `(u1 − u2)` 注释是**过期注释**，删掉即可
- 实测**同号** ⇒ 代码要改成 `(u1 − u2)`，同时 `U2_Geom2Motor` 必须跟着反号（两者是严格反函数，改一个必须改另一个）

**这一步没做，逆解出来的角度可能整个偏掉。**

### 5.4 用实测坐标验证正解

1. 摆 3 个已知姿态，记录 u1、u2（从 `Unitree_motors[x].data.position` 读）
2. 用卷尺量出末端实际 (x, y)（相对肩关节，单位 mm）
3. 对比 `Forward(u1, u2)` 的输出

若偏差整体呈"旋转一个固定角"→ `ZERO_POS` 错；
若偏差随关节角增大而放大 → `RATIO` 错；
若偏差是固定平移 → 肩关节原点定义与量测基准不一致。

## 7. 前瞻连续规划（取消段间停车）

### 7.1 现状为什么会停

`Target_Quintic_Interpolation` 的边界条件里写死了 `s′(1) = 0`、`s″(1) = 0`——**每段末尾速度必然归零**（设计如此，为了到点不撞不抖）。所以每到一个点位都要减速到零再重新起步。

`ARM_START_VELOCITY = 0.8` 是**半吊子前瞻**：它让每段起步带速度，但它是固定常数、不是上一段的出口速度，所以段间速度从 0 瞬跳到 `0.8 × Δθ / T`——既没做到连续，又留了一个速度阶跃。

### 7.2 完全版五次多项式系数（超集，兼容现有代码）

把边界条件改成 `s′(1) = v1`、`s″(1) = acc1`，仍然是 6 个条件 6 个系数，**同一个五次多项式就够**。用叠加法（同第 2 章）多解出两块：

| 来源 | 拆出的右边 b | 解 |
|------|-------------|-----|
| × **v1** | `(0, +1, 0)` | `(−4, +7, −3)` |
| × **acc1** | `(0, 0, +1)` | `(+0.5, −1, +0.5)` |

叠加得完全版系数：

```c
a1 = v0;
a2 = 0.5f * acc0;
a3 = 10.0f - 6.0f*v0 - 1.5f*acc0 - 4.0f*v1 + 0.5f*acc1;
a4 = -15.0f + 8.0f*v0 + 1.5f*acc0 + 7.0f*v1 - 1.0f*acc1;
a5 = 6.0f - 3.0f*v0 - 0.5f*acc0 - 3.0f*v1 + 0.5f*acc1;
```

**自检**：令 `v1 = acc1 = 0` 立即回落到 `seize_sky.c:99-101` 的现有写法 ✓ —— 是严格超集，不是换算法。

### 7.3 两种"不停"的做法（别混淆）

| 做法 | 位置精度 | 代价 |
|------|---------|------|
| **(a) 拐点带速度通过**（本节方案） | **仍精确经过**（`s(1) = 1` 不变） | 该点位没有停留，是"扫过"不是"停住" |
| (b) 圆弧 / Bézier 圆滑过渡 | 真的削角，偏离 ≤ 过渡半径 δ | 中间点被抄近路绕过 |

**抓块点、放块点（`LOW`/`LOW1`/`MID`/`MID1`/`HIGH`/`SKY`）两种都不能用，必须 `v = 0`。** 只有纯过渡位姿（`READY`/`SKY_READY`/`KEEP` 这类）才能带速度拐过去。若状态序列每段两头都是抓放点，"每段都停"本就是正确做法。

### 7.4 收益量级（算例）

三个路径点、u2 累计 1.22 rad：

| 指标 | 每段独立（现状） | 前瞻连续 |
|------|-----------------|---------|
| 总时长 | 3.0 s | **2.25 s（−25%）** |
| 拐点速度 | 0 | 0.30 rad/s（各轴按 Δθ/T 匹配） |
| 段内峰值 `s′` | 1.875 | ~1.44（−23%） |
| 物理峰值速度 | 0.66 / 0.94 / 0.69 rad/s | 0.75 / 0.99 / 0.79 rad/s（+10%~15%） |

逻辑：峰值归一化速度从 1.875 降到 ~1.44 ⇒ 在同一关节速度上限下段时长可压到约 77%。

推导：保持同一物理峰值速度 `v_phys = Δθ·s′_peak / T` 不变时，`T_new / T_old = s′_peak_new / s′_peak_old`。实测几个配置（脚本复算过）：

| `v0 = v1` | 峰值 `s′` | `T` 可压到 |
|-----------|----------|-----------|
| 0（现状全零版） | 1.8750 | 100% |
| 0.45 | 1.4813 | 79% |
| 0.5 | 1.4375 | 76.7% |
| 现状 `v0=0.8` | 1.5954 | 85%（但终点仍归零，段间不连续） |

### 7.5 实测算例：一条动作链到底在哪里卡

**先定义"接缝时刻"**：上一段的 `time` 达到 `total_time`（`seize_sky.c:164`）与下一段的 `time = 0`（`:118`）是**同一个物理时刻**。位置连续（都在目标位上），**不连续的是速度**。

以 `READY → MID → KEEP → HIGH` 为例（L1/L2 与标定常量按当前占位值，`dj` 单位度）。假设上位机每条命令固定等 200 ms：

| 段 | T | Δdj | 起点跳变 `0.8·Δθ/T` | 峰值 `1.5954·Δθ/T` | 起点加速度阶跃 `4.6·Δθ/T²` |
|---|---|---|---|---|---|
| ① READY→MID | 1.0 s | +89.3° | **+71.4 °/s** | 142.5 °/s | 411 °/s² |
| ② MID→KEEP | 1.0 s | −126.3° | **−101.0 °/s** | 201.5 °/s | **581 °/s²** |
| ③ KEEP→HIGH | 2.0 s | +108.3° | **+43.3 °/s** | 86.4 °/s | 125 °/s² |

**同一个 `ARM_START_VELOCITY = 0.8`，在 ① 上跳出 71 °/s，在 ③ 上只跳 43 °/s** —— 因为它是归一化常数，跳变量完全由 `Δθ/T` 决定，一个宏管不住三段。

接缝处实际发生三件事，性质不同：

| # | 现象 | 触发点 | 是不是 bug |
|---|------|--------|-----------|
| ① | 后半段持续减速，末尾**速度归零** | `s′(1) = 0` 是五次多项式的硬性边界条件 | 不是。设计如此，到点不撞不抖 |
| ② | 两段之间**完全静止** | `finish = true` 后 `running = false`，`Update` 直接 `return`（`:151-154`），机械臂等着上位机 | 取决于上位机定时 |
| ③ | 每段起点速度**从 0 跳起** | `s′(0) = v0 = 0.8` 固定常数（`:14`） | **是**。这是真正的不连续 |

**关键结论：前瞻让 ③ 消失（`v1 = v0'`，接缝处速度只剩一个值），但 ② 只能靠"到位反馈"消除，① 则在抓放点必须保留。**

若拐点速度定为 60 °/s（物理单位，各段再换算成自己的归一化 `v0/v1`）：

| 段 | 归一化 `v1`（上一段出口） | 归一化 `v0`（下一段入口） | 结果 |
|---|---|---|---|
| ① READY→MID | 60 / 89.3 = 0.672 | — | 段内峰值 116 °/s（比现状 142.5 更低） |
| ② MID→KEEP | — | 60 / 126.3 = 0.475 | 段内峰值 205 °/s（比现状 201.5 略高） |

注意：**同一个物理拐点速度，在两段里对应的归一化值不同**（0.672 vs 0.475）——这正是为什么前瞻需要一个"规划器"来统一决定每个拐点的**物理**速度，而不是简单地给一个 `v0` 宏赋同一个数。

**前瞻只保证速度连续，不保证加速度连续。** 拐点处 `acc` 仍是折点（除非同时把 `acc1` 也匹配上），视觉上不会更抖，但听感上仍可能有一声轻响。

**顺带一个待确认项**：`MID` 的 `dj = −143.7°`、`KEEP = −270.0°`、`HIGH = −161.7°`，即 `MID → KEEP → HIGH` 要走 **−126.3° 再 +108.3°**，净变化只有 −18°。若 `dj` 是底座回转，这等于让底座来回摆 234.6°，`r ≈ 693 mm` 处夹爪多走约 2.8 m 弧长。是有意绕行（避障/换侧）还是点位没调好，值得确认。

### 7.5.1 常见误解：把动作分开用就不会有起步冲击？

**不会。** ③ 那个起步跳变**与两条命令之间隔多久完全无关**——`s′(0) = v0` 是每段自己的边界条件，不是"从上一段继承来的出口速度"。新轨迹一旦启动，第 1 个插补周期的指令速度就是 `0.8·Δθ/T`；前面站了 1 ms 还是 10 s，跳变高度一模一样。

| 现象 | 是否受"命令间隔"影响 |
|---|---|
| ① 段末减速归零 | ❌ 不受。每段都有 |
| ③ 段首速度跳变 | ❌ **不受。每段都有，高度只由 Δθ/T 决定** |
| ② 段间静止 | ✅ 受影响 —— 但**分开用只会让它变长，不会让它消失** |
| ④ 半途被打断（丢任务） | ✅ 受影响 —— **只有这一条是"分开用"能真正躲开的** |

同一动作链实算：段间各等 1.5 s 时整条链 **7.0 s**，紧接时 **4.0 s**。分开用要多付 3 秒白等，而三次起步跳变（71.4 / 101.0 / 43.3 °/s）**一次都没少**。

> 一句话：**"分开用"换到的是"旧动作不会被中途丢弃"，换不到"没有震动"。**

要让"分开用"真正干净，只有一条路：把 `ARM_START_VELOCITY` / `ARM_START_ACCEL` 从 `0.8 / 4.6` 改成 `0 / 0`，段首速度跳变直接归零，红色竖线整个消失。那时"分开用"的成本只剩"白等"这一项。

**实操判据**：跳变量正比于 `Δθ/T`，加速度阶跃正比于 `Δθ/T²`。把小行程和长行程混在一张表里看，就知道哪些段需要在意：

| 段 | Δdj | T | 速度跳变 `0.8·Δθ/T` | 加速度阶跃 `4.6·Δθ/T²` | 需要在意吗 |
|---|---|---|---|---|---|
| MID→MID1 | −10.0° | 1.0 s | 8.0 °/s | 46 °/s² | 不用 |
| READY→LOW | +11.0° | 1.0 s | 8.8 °/s | 51 °/s² | 不用 |
| LOW→LOW1 | −19.7° | 1.0 s | 15.8 °/s | 91 °/s² | 基本不用 |
| KEEP→HIGH | +108.3° | 2.0 s | 43.3 °/s | 125 °/s² | 稍注意 |
| SKY→KEEP | −65.0° | 1.0 s | 52.0 °/s | 299 °/s² | 要在意 |
| READY→MID | +89.3° | 1.0 s | 71.4 °/s | 411 °/s² | 要注意 |
| **MID→KEEP** | **−126.3°** | 1.0 s | **101.0 °/s** | **581 °/s²** | **明显** |

`u2` 那一路同样不可忽略：`MID→KEEP` 的 `Δu2 = 0.74 rad`，加速度阶跃 `4.6 × 0.74 = 3.4 rad/s²`（≈ 195 °/s²）。

### 7.6 前提：先有"到位反馈"

`Arm_Transmit()`（`seize_sky.c:923-962`）**只发 `level_flag` 一个字节**，没有任何到位/完成标志。上位机因此只能靠定时发下一条命令——定时偏短会不停打断上一段，偏长则把省下的时间全吃掉。**加一个"到位"字节（`ArmControl.state` 或 `finish`）是比前瞻更优先的事。**

### 7.7 适用判据：什么时候**需要**前瞻、什么时候**完全不需要**

**正面回答**：

| 你的说法 | 判断 |
|---|---|
| 每段做完等一会再发下一条 ⇒ 不需要前瞻 | ✅ **对** |
| 一段紧挨一段发 ⇒ 就需要前瞻 | ❌ **不对**。"紧挨着"只是**必要条件**，不是充分条件 |

**第一句为什么对**：前瞻的本质是"把两段各自的减速 + 加速合并掉"。你主动在两段之间留了间隔 ⇒ 接缝速度本来就落在 0（`s′(1) = 0` 是硬边界条件）⇒ **没有重复劳动可省，前瞻无事可做**。

**第二句为什么不对**：紧挨着只让前瞻**有可能**帮上忙。它要真帮得上，必须**同时**满足三条：

| # | 必要条件 | 你的工程 |
|---|---|---|
| 1 | 段与段之间**没有停顿** | 紧挨着发时有 ✔ |
| 2 | 接缝处**每个关节都同向**（不能有轴掉头） | `READY→MID→KEEP→HIGH`：MID 接缝 u1 反向、dj 反向；KEEP 接缝 u1 反向、dj 反向 ❌ |
| 3 | 系统**提前知道"后面还有一段"**（队列 / 预加载） | 无队列 ❌ |

**第 2 条是硬约束**：三条轴共用同一个 `s(t)`（`seize_sky.c:157-163` 用同一个 `time`、同一个 `total_time`），接缝时刻只能有**一个**速度值。只要有任意一路必须反向，这个接缝就必须零速——调宏、调参都救不了。量化判据就是 8.5 那条：

```
v² / (2a) ≤ S       刹车距离不得超过剩余行程；且关节反号 ⇒ 必经零速
```

**第 3 条最常被忽略**：前瞻是**规划期**的技术，必须先知道下一段长什么样，才算得出"这个接缝允许多少速度"。所以它要求**队列 / 预加载**，而不是"跑完立刻发下一条"——后者接缝仍是 `s′(1) = 0`，等于没省。

**再分清楚一件事：前瞻 ≠ 打断**

| | 前瞻 | 打断 |
|---|---|---|
| 旧轨迹 | **保留**，接缝处速度连续 | **作废**（`:561-566` 换挡重置，剩余路程直接丢弃） |
| 是否要知道下一段 | **需要**（否则谈不上接缝规划） | **不需要**（恰恰是来不及 / 不想知道） |
| 结果 | 机械臂"拐"过去 | 从当前位置另起一段，跳变见 8.5 / 8.6 |

两者方向相反。所以"中途打断"再用得多，也变不成前瞻。

**收束**

> **等待 ⇒ 前瞻没用（对）；紧挨着 ⇒ 前瞻也不一定有用（错在"一定"）。** 你的接缝在 MID / KEEP 都有关节反向，第 2 条直接卡死，**收益为 0**——无论紧不紧着发。

真要省时间，别绕前瞻：把 `ARM_MOVE_TIME` 从固定 1 s 改成**按行程算**（`Δθ` 大的给长、小的给短，上限就取你现在已在跑的峰值速度：u2 2.0 rad/s、dj 210 °/s）：

| 段 | 现在 | 按行程定 | 受谁限制 |
|---|---|---|---|
| READY→MID | 1.0 s | **0.68 s** | dj |
| MID→KEEP | 1.0 s | 0.96 s | dj |
| KEEP→HIGH | 2.0 s | **0.82 s** | dj |
| **合计** | **4.0 s** | **2.46 s** | **省 1.54 s（38%）** |

形式就是一行，不动算法：

```c
float T_move = CLAMP(fabsf(dth) / fmaxf(fabsf(v_max), 0.05f), 0.4f, 3.0f);
```

**38% 对前瞻的 0%**——这是当前工程里性价比最高的时间优化。

## 8. 中途切换动作：行为与静默失败点

### 8.1 成功的路径（延迟 1~2 ms）

```
Arm_Receive（中断）置标志
  → Arm_State_Update（TIM2 1kHz）优先级链 reset > ready > keep > pick > place 改 state
  → Arm_Control_Task（1ms）state != last_state → running=false; finish=false   （:561-566）
  → 同一轮 switch 派发新 Process → 守卫放行 → Start()
  → start_angle 从电机反馈现读 → 新轨迹从"此刻实际位置"拐向新目标
```

### 8.2 四种静默失败

| 情况 | 位置 | 结果 |
|------|------|------|
| 目标状态 == 当前状态（如在 `LOW` 时重发取块，`level_flag=1` → 仍是 `LOW`） | `:469-473` | state 不变 → 换挡检测不触发 → 守卫不通过 → **什么都不发生** |
| 两条命令间隔 < 1 ms | state 在 ISR 改，任务 1 ms 轮询 | 任务只看到最后一条，**前一条被无声吞掉** |
| `Is_pick` 与 `Is_place` 同时为 1 | 两个 `if` 均不成立 → `:530-535` | 末尾统一清零，**命令被丢弃** |
| `Is_on == 0`（'D' 失能） | Process 不受门控（`:603-666`），`Update` 受门控（`:667-674`） | `running=true` 但 `time` 停在 0；复使能后从**旧 `start_angle`** 重算 → **跳变** |
| `data.position` 无效（反馈帧 P0） | `:110-111` | `start_angle` 恒 0，"从当前位置起跑"失效 → 中途切换表现为**猛抽** |

### 8.3 切换 = 放弃，不是排队

没有命令队列，也没有"跑完再做下一条"的语义。旧动作剩余路程直接丢弃，从半路拐向新目标。因此：

- "取块跑到 30% 时发放块" ⇒ **直接拐去放块位，块没抓到**
- `state` 只代表目标位姿，不代表任务语义完成（夹爪由 `Is_open` 单独控制，可能不一致）
- 实际命令链 `P`(准备) → `T`(取块+夹紧) → `H`(持块) → `F`(放块准备) → `R`(松爪)：若 `T`/`H` 之间只靠固定定时，`H` 可能在**尚未到达抓块位姿**时就把动作切走 → 夹爪到位时块不在爪里

### 8.4 修法（按性价比）

1. **加"到位"反馈**（最优先）：`tx_data` 加一字节 = `ArmControl.state`，或把 `finish` 作为到位位发出；上位机收到到位再发下一条
2. **让重发同一动作生效**：`Arm_State_Update` 中对相同状态也重新解锁（置 `finish=false`），或引入命令序号
3. **保证命令间隔 > 1~2 ms**
4. **修 `data.position`（P0 反馈帧位域）**，否则 1、2 都无效
5. 真正的排队只能在上位机侧做（MCU 侧加队列要改状态机结构，收益不高）

### 8.5 被打断瞬间，速度必须降到零吗？

**分两层回答：位置层不必，速度层必然跳变（当前代码如此）。**

#### 位置是连续的

`Arm_Interpolation_Start`（`seize_sky.c:118-137`）的起点是**从电机反馈现读的当前实际位置**：

```c
ArmControl.u1.start_angle = Unitree_motors[0].data.position;
```

所以被打断时不会瞬移，新段从"此刻实际在哪"起跑。

> ⚠️ 前提是 `data.position` 有效。若反馈帧位域 P0 未修（帧长 18 ≠ 协议 16 字节），这里读到的是垃圾值，"位置连续"整条结论都不成立——**打断会表现为猛抽**。先修这个再看下面的内容。

#### 速度是**跳变**的

`Start` 里唯一与速度相关的只有 `v0 = ARM_START_VELOCITY = 0.8`，它是**归一化常数**，跟"此刻电机实际多快"毫无关系。而且 `Start` **根本不读速度反馈**。于是：

- 旧段在打断时刻的真实速度 = `Δθ_old × s′(t_int/T_old) / T_old`（一般非零，峰值附近可达自身峰值）
- 新段第一个周期的指令速度 = `Δθ_new × 0.8 / T_new`（另一个毫不相干的数）

**两者之间没有任何桥接 ⇒ 一个控制周期内完成速度突变。**

#### 实测算例：MID→KEEP 在 t = 0.35 s 被 HIGH 打断

`Δdj = −126.3°`、`T = 1 s`，`s(0.35) = 0.4702`、`s′(0.35) = 1.5912`（接近峰值 1.5954）：

| 关节 | 打断时刻位置 | 打断时刻速度 | 新段 Δ | 新段指令初速 | **跳变** |
|---|---|---|---|---|---|
| u1 | 1.239 rad | **−0.239 rad/s** | +0.091 | +0.036 | **+0.275** |
| u2 | 0.328 rad | **+1.178 rad/s** | +0.852 | +0.341 | **−0.837** |
| dj | −203.08° | **−200.97 °/s** | +41.38 | +16.55 | **+217.5 °/s** |

**对照"等完成再发"**（`KEEP→HIGH`，`Δdj = +108.3°`、`T = 2 s`）：跳变只有 **43.3 °/s**。

> **所以打断并没有"省掉减速"——它反而把跳变放大了 5 倍**（217.5 vs 43.3），而且三个关节里有两路是**反向**跳变。
> 原因：新段因为"已经走了一段"而变短（dj 只剩 41.4° 而不是 108.3°），`Δθ_new × 0.8 / T_new` 也随之变小，但**旧段的速度还在峰值附近**。两头一凑，落差反而最大。

#### 三种策略对比（同一段打断）

| 策略 | dj 跳变 | 总耗时 | 说明 |
|---|---|---|---|
| **(a) 等完成再发** | 43.3 °/s | 3.00 s | 旧段自然减速到 0，无反向跳变 |
| **(b) 当前代码打断** | **217.5 °/s（反向）** | 2.35 s | 省了 0.65 s，代价是 5 倍冲击 |
| **(c) 正确打断（先刹车）** | 0（连续） | **1.42 s** | 又平顺又快 |

**(c) 怎么做**（用旧段的减速能力 `a = 4.6 × 126.3 / 1² ≈ 581 °/s²`）：

1. 保持原方向继续减速：`v²/(2a) = 201.0²/(2×581) = **34.8°**`，耗时 `201.0/581 = 0.346 s`，dj 走到 **−237.8°**（比 KEEP 还多走 32° 的"过冲"）
2. 从 −237.8° 反向加速到 HIGH 的 −161.7°，行程 76.1°，三角速度剖面耗时 `2√(76.1/581) = 0.724 s`

合计 **1.07 s 运动 + 首段 0.35 s = 1.42 s**，比 (b) 快 0.93 s，且速度全程连续。

**代价是那 34.8° 的额外过冲行程**——必须确认机构余量容得下。

#### 打断准入判据

想判断"此刻能不能安全打断"，只需一个式子：

```
需要的刹车距离 = v² / (2·a_max)   ≤   允许的额外过冲行程 S
```

| 打断时的 dj 速度 | 需要刹车距离 | 是否可接受（假设 S ≈ 20°） |
|---|---|---|
| 50 °/s | 2.2° | ✅ 随便打 |
| 100 °/s | 8.6° | ✅ |
| 150 °/s | 19.4° | ⚠️ 临界 |
| 201.5 °/s（本段峰值） | **34.9°** | ❌ 会撞限位或来不及 |

对应到时间轴上：**每段开始后 0~0.15 s 和结束前 0.15 s 是"打断安全窗口"（速度低），中间 0.2~0.8 s 是"危险窗口"（速度接近峰值）。**

#### 所以前瞻对这个场景有用吗？——**离线前瞻没用，它的内核有用**

| 工具 | 打断场景能否用 |
|---|---|
| **离线前瞻**（跑到前面预规划整条链的拐点速度） | ❌ 用不上。打断是**运行时事件**，执行器不知道未来路径，没法"提前规划" |
| **速度交接 / 速度继承**（把当前实际速度当新段的 `v0`） | ✅ **正是这里需要的** |
| **反向判据 + 可行性检查**（`v²/2a ≤ S`，关节反号必过零） | ✅ 正是这里需要的 |

也就是说：**打断场景需要的是"在线前瞻"——单段带初速规划 + 准入检查**，而不是"离线多段前瞻"。

而实现"速度交接"所需的数学，**第 7.2 节那个完全版五次多项式已经够了**（`v0/acc0` 本来就是它的输入）。要改的只有 `Arm_Interpolation_Start`：

```c
// 现状：v0 写死
ArmControl.u1.start_angle = Unitree_motors[0].data.position;

// 速度交接版（示意，注意归一化与限幅）
float v_now = Unitree_motors[0].data.speed;                 // 关节侧 rad/s（UnitreeMotor.c:277 已除减速比）
float dth   = u1_target - Unitree_motors[0].data.position;  // rad
ArmControl.u1.v0 = CLAMP(v_now * ArmControl.total_time / dth, -1.0f, 1.0f);
```

⚠️ **三个坑**：
1. `v0` 是**归一化**量（`v0_norm = v_phys × T / Δθ`），必须除 `Δθ`。`Δθ` 很小时 `v0_norm` 会爆掉 → **必须限幅**，否则多项式非单调、会冲过目标再拐回来
2. 速度与目标**反号**时不能直接继承（上面 dj 就是这种：`−201` 而目标在前方），必须先走"刹车 + 反向"，也就是 (c) 的两段式
3. 三条轴共用 `s(t)`，所以**三条轴必须用同一个 `v0` 才有意义**——而三条轴的"物理速度 ÷ 行程"比值一般不同，**做不到同时交接**。这与 7.5 节"关节反号必停"是同一个结构约束。**只要有一路必须停，那一停就通过共用 `s` 传导给全部三路。**

#### 结论

| 你的问法 | 答案 |
|---|---|
| 每段执行完等一会 ⇒ 不需要前瞻 | ✅ 对（完整判据见 **7.7**） |
| 每段紧密挨着 ⇒ 需要前瞻 | ⚠️ **必要但不充分**：还需"接缝处三轴同向"+"提前知道下一段"。7.5 节扫描结果：你的点位表在 MID / KEEP 都反向，**收益为 0**（完整三条必要条件见 **7.7**） |
| 打断时速度必须降到零吗 | ❌ **不必降到零**，但会**跳过所有中间过渡**，在当前代码里表现为 217 °/s 的反向阶跃 |
| 前瞻对打断有用吗 | **离线前瞻没用**；前瞻的**内核**（速度交接 + 准入判据）正是这里该做的——而且按判据看，**最省事的做法往往是"别在这时打断，等 0.2 s"** |

### 8.6 只看两个宇树（u1 / u2）时的结论——和 dj 不一样

上面 8.5 的算例里 dj 最刺眼（217 °/s 反向阶跃），但**把 dj 摘掉只留宇树两路，结论会变成另一套**。

前提确认：驱动反馈字段是 `data.speed`（**关节侧** rad/s，`UnitreeMotor.c:277` 已除 `UNITREE_GEAR_RATIO`），而 `Arm_Interpolation_Start` **完全没有读它**。

算例仍取 `MID→KEEP`（`Δu1 = −0.15`、`Δu2 = +0.74`，T = 1 s）在 `t = 0.35 s` 被 HIGH 打断。打断瞬间：`s = 0.4702`、`s′ = 1.5912`。

#### 一、u1 必定**反向**，u2 必定**同向塌陷**

| 关节 | 打断时刻位置 | 打断时刻速度 | 新段 Δ | 新段指令初速 | 跳变 | 反号？ |
|---|---|---|---|---|---|---|
| **u1** | 1.2395 rad | **−0.2387 rad/s** | +0.0905 | +0.0362 | **+0.2749** | **是（反向）** |
| **u2** | 0.3279 rad | **+1.1775 rad/s** | +0.8521 | +0.3408 | **−0.8367** | 否（同向） |

**u1 的反向和打断时刻无关。** 扫遍 `t = 0.05 ~ 0.95`，u1 全部判为"是"：因为旧段 `Δu1 = −0.15`（往负走），而新段目标是 `HIGH` 的 1.33 > 当前位置，**新段必定往正走** ⇒ 只要在段中途打断，u1 一定得掉头。

量级：
- **u1 跳变 0.2749 = 它自己本段峰值 (0.15×1.5954 = 0.2393) 的 115%** ⇒ 速度完全反号
- **u2 跳变 0.8367 = 它自己本段峰值 (0.74×1.5954 = 1.1806) 的 71%** ⇒ 速度从 1.1775 塌到 0.3408，只剩 29%。**这不是"反向冲击"，是"速度瞬间塌陷"**——物理上比反向温和得多

#### 二、u2 本来能平滑交接，是被 u1 拖累的

三条轴共用同一个 `s(t)`（`Arm_Interpolation_Update` 里三次调用用同一个 `time`/`total_time`），所以接缝处**只能有一个 `v0`**。反算两路各自"想接住自己的速度"所需的 `v0`：

```
v0 = v_actual × T / Δθ_new

u2: 1.1775 × 2 / 0.8521 = +2.76      （想接住）
u1: −0.2387 × 2 / 0.0905 = −5.28     （想接住 / 不反向）
```

**两者相差 8.0，一个数不可能同时满足。** 这正是"共享 `s`"的结构约束在数量上的体现：

- 取 `v0 = 0` → u2 指令初速 0，跳变 −1.1775（**更糟**）
- 取 `v0 = 0.8` → u2 跳变 −0.8367、u1 跳变 +0.2749（现状，两边都没搞定）
- 想让 `|v0| ≤ 1`（五次多项式还能保持单调），就只能**把 T 缩短**

#### 三、T 不该写死——按当前速度反推

| 打断后新段 T | cmd u1 | u1 跳变 | cmd u2 | u2 跳变 |
|---|---|---|---|---|
| 2.00 s（现状） | +0.0362 | +0.2749 | +0.3408 | **−0.8367** |
| 1.00 s | +0.0724 | +0.3111 | +0.6817 | −0.4958 |
| **0.72 s** | +0.1006 | +0.3393 | **+0.9468** | **−0.2307** |

`T = 0.72 s` 的来历：`Δθ_new / v_actual = 0.8521 / 1.1775 = 0.72`，即"用当前速度刚好走完剩余行程所需的时间"。取 `T` 略大于它、`v0 ≈ 1`，新段就能以接近当前速度起步。

**结论：u2 的跳变从 −0.84 降到 −0.23（降 72%），代价是 u1 的跳变略升（0.275 → 0.339，而它反正要反向）。** 一句可执行的规则：

```c
// 打断时不要传死值，按当前速度算
float T_move = CLAMP(fabsf(dth) / fmaxf(fabsf(v_now), 0.05f), 0.4f, 3.0f);
```

#### 四、好消息：宇树这两路**刹车余量充足**

用本段自身的峰值加速度当上限（`a = acc0 × |Δθ| / T²`）：`a_u1 = 0.690 rad/s²`、`a_u2 = 3.404 rad/s²`。

| 关节 | 需要刹车距离 `v²/(2a)` | 新段剩余行程 | 余量 |
|---|---|---|---|
| u2 | 0.2037 rad | 0.8521 rad | **4.2 倍** |
| u1 | 0.0413 rad | 0.0905 rad | **2.2 倍** |

所以对宇树来说"**先刹住再走**"完全可行（不像 dj 那样骑在临界上）。要额外付出的只是 u1 的 41 mrad（≈2.4°）反向过冲。

#### 五、最要紧的一条：现在根本**没有"安全打断窗口"**

看面板①那张归一化速度图——**因为 `v0 = 0.8`，段的起点速度就已经是峰值的 50%**，`t = 0.1` 就爬到 75%：

| 段进度 t | |s′| 占峰值（v0=0.8） | |s′| 占峰值（v0=0） |
|---|---|---|
| 0.00 | **50%** | 0% |
| 0.10 | 75% | 13% |
| 0.20 | 92% | 41% |
| 0.35 | **100%** | 83% |
| 0.70 | 47% | 71% |
| 0.85 | 15% | 26% |
| 0.90 | 7% | 13% |

- 现状：只有 `t > 0.80` 这**最后 20%** 是低速区 ⇒ 想安全打断几乎只能等它快跑完
- `v0/acc0` 归零后：`t < 0.21` **也变成低速区**，段的两头都可打断

**所以"把 `v0` 归零"这条建议多了一个之前没提到的附带收益——它顺手把"打断"从不可行变成可行。** 而打断时机的最差点恰好是 `t ≈ 0.35`，也就是段中点、"急着打断"最常落到的位置。

#### 六、宇树两路的收束

| 问题 | 答案 |
|---|---|
| 打断时 u1/u2 的速度必须降到零吗 | **位置不必，但 u1 一定掉头**（跳变 = 自身峰值 115%）；u2 是**同向塌陷**（掉到 29%），不反向 |
| dj 和宇树哪一路更糟 | **量级不可直接比**（dj 是 °/s，宇树是 rad/s）。按"占自身峰值比"看：u1 115% > dj …，但**宇树的绝对速度和惯量都小得多**，冲击等级要低 |
| 打断 vs 等完成 | u1 跳变 0.275 vs 0.068（**4 倍**）；u2 跳变 0.837 vs 0.184（**4.5 倍**）。**结论不变：打断更冲** |
| 宇树两路能不能做到平滑打断 | **单看余量可以（4.2 / 2.2 倍），但共享 `s` 让它做不到**——除非给每轴独立的 `s(t)` |
| 该先做哪件 | ① `v0/acc0` 归零（顺带造出打断窗口）；② 打断时按 `Δθ/v_now` 算 `T`、并读 `data.speed` 做速度交接；③ 修 `data.position` 的反馈帧 P0，否则 ①② 都建立在垃圾数据上 |
