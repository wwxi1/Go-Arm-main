# 机械臂调试：先看波形，再看事件

适用工程：`Go_Arm_Final/Go-Arm-main/Go-Arm-main`。
这里已经接入代码，不需要照着教程再实现一遍。尚未连接实机验证。

## 0. 这一版到底完成了什么

- VOFA：修正 DMA 双缓冲和忙判断，默认发送两只宇树的六个量。
- 接收时间戳：每只宇树在收到有效回包时更新，和波形发送无关。
- RAM 记录：最近 16 个事件；第一次异常另存一份，后续异常不覆盖。
- Event Recorder：已经加入官方源码和 Keil 工程，记录动作事件，不依赖 printf/蓝牙。
- 动作结束原因：指令发完、目标非法、人工取消、被新动作替换、请求复位。
- 人工禁用：取消旧轨迹，重新使能不自动续跑这段旧轨迹，需要明确的新动作。
- 拒绝非有限数、非正运动时间和不可达坐标；保留原点表、插值参数和时间推进方式。

**这版是调试观测与有限的输入检查，不是完整的人身安全系统。**
反馈超时只告警，不新增失能/制动/断电动作；承重轴的处置尚需实机确定。
没有自动到位成功判定，没有完整机械限位/碰撞检查，也没有自动堵转保护。
不可达/非法输入退出只停止生成新轨迹点，驱动可能仍保持此前目标，不能当作急停。
DJI 的反馈时间戳和整机通信心跳暂未统一接入。

## 1. 先弄清楚数据在哪

```text
宇树回包
  → s_unitree_rx_data（解析临时变量，下一只电机回包会覆盖它）
  → Unitree_motors[id].data（按电机编号保存反馈）
  → Unitree_link[id]（同时保存接收时间和有效帧计数）
  → VOFA/故障快照读取这些变量
```

不要拿 `s_unitree_rx_data` 当电机 0 的持续反馈，它可能下一刻属于电机 1。
`Unitree_motors[0].cmd.position` 是当前轨迹指令；`.data.position` 是对应反馈。
`correct=1` 说明保存的那次帧校验成功，不说明现在仍在线。

RAM 就是 STM32 存变量的内存。例如 `ArmControl`、`g_arm_diag` 都在 RAM。
复制到 `g_arm_diag.first_fault` 就完成了“RAM 保存”，不需要存储驱动。
普通 RAM 断电丢失，复位/重新下载也可能覆盖。本版日志按本次启动使用，不承诺跨复位保存。

## 2. 第一次上手：先不要动机构

首次使用 Keil 和 VOFA，请先看 [Keil与VOFA首次操作](Keil与VOFA首次操作.md)，里面按点击顺序列出设置和预期现象。
2026-09-24 补正：`Core/Src/freertos.c` 原来注释了 VOFA 的 `osThreadNew`，现已启用；此前仅修改发送函数不足以让任务运行。

1. 打开 `MDK-ARM/27RC_Proj_Template.uvprojx`，Build。
2. 使用现有 ST-LINK/J-Link 接线和项目设置连接。确认调试对象是这份最新工程。
3. 在机构处于安全条件下下载；这里的代码修改没有替你下载或驱动机构。
4. 进入 Debug，在 View → Watch Windows → Watch 1 中添加下面的变量：

| Watch 项 | 如何解释 |
|---|---|
| `Unitree_link[0]`、`Unitree_link[1]` | `seen=1` 表示收过有效帧；`rx_count` 应持续增加 |
| `g_arm_diag.latest.age_ms[0]`、`[1]` | 最近反馈距今的毫秒数；4294967295 表示还没收过 |
| `g_arm_diag.latest.position` | 两只电机反馈角度，rad |
| `g_arm_diag.result` | 动作生成器结果，见后面的表 |
| `g_arm_diag.event_init_ok` | Event Recorder 初始化成功应为 1 |
| `vofa_sent_count` | 成功启动 DMA 的次数，不是电脑确认收到的次数 |
| `vofa_skipped_count` | 上一包仍忙，这次跳过的次数 |
| `vofa_start_error_count` | HAL 启动发送失败的次数 |

5. Run。角度静止时，`rx_count` 也应该更新。不要为看变量随意 Halt 正在运动的控制器。
6. 故障发生后先按已验证的方法让机构安全停止，再查看/导出数据，不要先复位。

## 3. VOFA：看曲线，不需要自己挑第一组变量

六通道 = 同一包中的六个浮点数，不是六根线，也不是只能接六个电机。
六只是当前工程选定的数量，不是 VOFA 或 Event Recorder 的限制。增加数量时要同时调整采样填充代码、打包配置和串口带宽；现在先用这六个。
本版已填好默认通道，直接使用：

| 通道 | 默认配置 `g_diag_vofa_profile=0` | 单电机配置 `=1`（电机0）或 `=2`（电机1） |
|---|---|---|
| 0 | 电机0当前目标角 rad | 该电机当前目标角 rad |
| 1 | 电机0反馈角 rad | 该电机反馈角 rad |
| 2 | 电机1当前目标角 rad | 反馈速度 rad/s |
| 3 | 电机1反馈角 rad | 反馈力矩 Nm（当前驱动换算值） |
| 4 | 电机0反馈力矩 Nm | 反馈年龄 ms；-1 表示从未收到 |
| 5 | 电机1反馈力矩 Nm | 当前动作状态编号 |

操作：

1. UART9 PD15/TX 接 USB-TTL RX，GND 共地，确认电平兼容；不要误接 RS232 电平。
2. VOFA 选对应 COM 口，115200、8 数据位、1 停止位、无校验，协议 **JustFloat**。
3. 添加波形图：第一张勾通道 0/1，第二张勾 2/3，力矩另放一张看 4/5。
4. 当前任务约每 10 ms 发一次；波形 Δt 设置为相应单位的 10 ms。
5. 只执行一个已验证的小动作，看目标与反馈是否跟随。不要用真实卡死、撞限位验证日志。
6. 想细看电机0时，停止这次采集，在 Watch 将 `g_diag_vofa_profile` 改为 1，再重新开始记录。
   profile=2 同理看电机1。不要在同一段曲线中途换含义。

这里的“目标”是当前插值点，不是点表中的最终目标。误差应比较同一时刻的目标和反馈。
正常情况下，目标曲线变化，反馈跟随它；不能要求任意工况两条线完全重合。
10 ms 是显示采样，不是保护响应期限。短于采样间隔的尖峰可能漏掉。
串口丢帧时，按固定 Δt 显示的时间轴不再完全准确；严谨分析时需另加序号/采样时间或使用 RAM 采样。

默认一包 28 字节，100 Hz 为 2800 字节/秒；115200、8N1 理论上限约 11520 字节/秒。
这只是串口带宽估算，不等于 CPU 占用率。实际时序须在板上测量。

### 为什么修 VOFA

旧定义 `[28][2]` 按两块 28 字节使用，两个起点只差 2 字节，互相覆盖。
现在是两块独立、32 字节对齐的缓冲，实际发送 28 字节；缓存维护覆盖完整独立缓存行。
旧忙标志只检查/清除，从未置忙。现在在启动 DMA 前置忙，启动失败清忙，完成回调清忙。
忙时丢弃一帧，不等待、不堆积。串口故障导致无法完成时，本版会保持不覆盖缓冲；应停稳后检查串口/DMA，不以超时强行复用仍被 DMA 占用的内存。

## 4. Event Recorder：给动作按顺序记下“发生了什么”

不是自动打印所有变量，也不是另一套波形工具。例如同一次动作：

| 相对时间（示意） | 事件 | 含义 |
|---|---|---|
| 0 s | TrajectoryStart，state=5，duration_ms=5000 | 开始持块姿态轨迹 |
| 约5 s | CommandsSent_ArrivalUnverified，result=2 | 轨迹指令发完，尚未确认实际到位；不是到位失败 |

另一次你中途禁用，会看到 `Cancelled`。目标坐标不可达会看到 `InvalidTarget`。
**VOFA 回答“角度怎么变”；Event Recorder 回答“什么时候开始/结束，为什么结束”。**

### 已经接好，不要重复勾选 RTE

工程已经包含 `ThirdParty/EventRecorder` 的官方 CMSIS-View 1.2.0 实现和配置。
不要再在 RTE 中加入第二份 EventRecorder.c，否则可能重复定义。
本版直接用 EventRecord2 记录两个整数，不经过 printf，不用 semihosting，不需要串口。
时间源为 HAL_GetTick，分辨率 1 ms，适合动作事件，不能用来测几微秒的函数耗时。
初始化在 `Arm_Control_Init()` 内调用 `ArmDiag_Init()`。

### 一条事件是怎样出现的

以开始动作为例，轨迹函数调用 `ArmDiag_Start()`，再进入 `ArmDiag_Record()`：

```c
/* 示意：事件编号 + 两个整数参数。实际调用已经封装好。 */
EventRecord2(EventID(EventLevelOp, 0x30U, ARM_EVT_START),
             (uint32_t)ArmControl.state, 5000U);
```

含义是“当前状态开始一段计划5000 ms的轨迹”。记录库同时取得时间戳，把事件放入 MCU 的 RAM 缓冲；Keil 经调试器读取它。SCVD 文件把编号翻译成 `TrajectoryStart` 等名称。
它不会自动知道“为什么电机没动”：程序在哪个判断分支主动记录了事件，你才能看到那个判断。也可以记录变量值，但本版将连续变量交给 VOFA，将开始、结束、异常交给 Event Recorder，减少重复采集。

### Keil 窗口操作

1. 正常连接调试器进入 Debug 并 Run。
2. View → Analysis Windows → Event Recorder。
3. 为了显示可读名称，进入 Options for Target → Debug →
   **Manage Component Viewer Description Files**，添加 `MDK-ARM/ArmDiagnostics.scvd`。
   不同 Keil 版本按钮位置可能略有变化；没有加载文件时仍可按十六进制 ID 对照下面的表。
4. 过滤器中查看 component 0x30（Arm），无需打开所有 FreeRTOS 事件。
5. 先确认 Boot 事件，再执行一次已验证动作，查看 Start 和 End/Cancel。

| ID | 名称 | val1 / val2 |
|---|---|---|
| 0x3000 | Boot | 当前状态 / 0 |
| 0x3001 | TrajectoryStart | 当前状态 / 计划毫秒数 |
| 0x3002 | CommandsSent_ArrivalUnverified | 当前状态 / 2 |
| 0x3003 | InvalidTarget | 当前状态 / 3 |
| 0x3004 | Cancelled | 当前状态 / 4 |
| 0x3005 | Superseded | 当前状态（可能已是新动作） / 5 |
| 0x3006 | ResetRequested | 当前状态 / 6 |
| 0x3007 | FeedbackTimeout_ALARM_ONLY | 当前状态 / 电机编号0或1 |
| 0x3008 | FeedbackRecovered | 当前状态 / 电机编号 |
| 0x3009 | DriveError | 当前状态 / 高16位为电机编号+1，低16位为驱动错误码 |
| 0x300A/B | Enabled / Disabled | 当前状态 / 使能请求 |
| 0x300C | ManualSnapshot | 当前状态 / 0 |

没有输出时检查：`event_init_ok=1`、窗口过滤器、调试器连接、代码是否执行到 ArmDiag_Init。
128 条 EventRecorder 记录约需 2212 字节（还包括管理数据），在预留 4 KB DTCM 区域内。
它是有限缓冲，长期不读取可能覆盖旧事件；不是永久日志。
SCVD 只负责把数字翻译成名称，不会参与电机控制。
`EventRecorderStop()` 停的是记录，不是电机。请求 MCU 复位后，本版 RAM 日志重新开始；不能保证复位前最后一条事件能送到电脑。

## 5. 接收时间戳怎么观察

有效帧通过包头/CRC/ID 校验后，更新：

```c
Unitree_link[id].last_valid_rx_ms = HAL_GetTick();
Unitree_link[id].rx_count++;
Unitree_link[id].seen = 1;
```

读取时用无符号减法 `now - last_valid_rx_ms` 算年龄；测试覆盖了计时器回绕。
一个短临界区同时复制反馈和时间戳，避免记录拼成“上一帧角度+下一帧时间”。
`Unitree_rx_bad_frames` 是不合格完整候选帧的总数，不代表所有线路噪声字节的计数。
CRC 已错误时不能信任帧内电机 ID，所以不强行把坏帧归到某只电机。

`g_diag_rx_timeout_ms=0` 默认不判超时，只显示年龄。
先测正常通信时年龄范围，再和主控确定阈值；确认后可在 Watch 改这个值做**告警观察**。
只有机构请求使能时才产生超时告警，持续异常只记一次，恢复后再次异常才重记。
阈值不是示波器发送周期，也不能从别人项目复制一个数。
本版不因它自动停机，不允许把这个观察功能当作保护已经生效。

## 6. 结束原因与 RAM 错误记录

Watch 中查看 `g_arm_diag.result`：

| 值 | 含义 |
|---|---|
| 0 | IDLE，尚未开始 |
| 1 | RUNNING，轨迹生成中 |
| 2 | COMMANDS_SENT，目标发完；不是 SUCCESS |
| 3 | INVALID_TARGET，数值/可达性检查不通过 |
| 4 | CANCELLED，禁用时取消正在执行的轨迹 |
| 5 | SUPERSEDED，被另一个动作替换；通常紧接新的 RUNNING |
| 6 | RESET_REQUESTED，请求复位；复位后普通 RAM 会初始化 |

`ArmControl.finish` 保留原有“流程结束”的用法，判断原因看 result 和事件。
禁用后取消旧轨迹，重新使能本身不续跑；发送明确的新动作指令后才能重新开始。
没有验证反馈到位，所以没有假造 SUCCESS 状态。当前结果也不是电机物理上“已停住”的证明。

### 查看日志不需要自己写文件

代码中的 `g_arm_diag.log[index] = rec;` 就是将一个事件结构体复制到 RAM 数组；`g_arm_diag.first_fault = rec;` 则单独保留首次异常。这和普通变量赋值一样，不需要 Flash 擦写或文件系统。
这份快照与 Event Recorder 的短事件记录是两份数据：事件窗口方便看顺序，Watch 展开快照方便看当时的多个变量。Event Recorder 不会自动展示任意结构体的所有成员。

- `g_arm_diag.latest`：约每10 ms更新的快照。
- `g_arm_diag.log`：最近16个事件，按 `sequence` 排序理解；`log_next` 是下一次写入下标。
- `g_arm_diag.first_fault_valid=1`：存在首次异常。
- `g_arm_diag.first_fault`：首次目标非法/反馈超时/驱动报错时的快照，不被后续故障覆盖。
- `g_arm_diag.action_elapsed_ms`：动作开始到结束的实际毫秒数。
- `g_arm_diag.max_task_period_ms`：两次机械臂任务循环的最大间隔，包含等待和调度，不是纯计算耗时。

在 Watch 展开 `first_fault.sample` 能看到目标、反馈、速度、力矩、反馈年龄、状态和DJI角度。
手动留一条证据：把 `g_diag_capture_request` 改为1；机械臂任务会复制快照并自动清零请求。
清记录：先失能，再把 `g_diag_clear_request` 改为1；使能时不会处理清除请求。
清除只清本版 RAM 事件/首次异常及周期最大值，不清 EventRecorder 历史或电机统计。
读取时不要先重启、下载。冻结的 first_fault 更适合查看；latest 正在变，Watch 的界面刷新不代表原子显示。

这只是事件时刻快照，不包含连续两秒的完整波形；只有确实缺少异常前过程，才值得加采样环形缓冲。

## 7. 怎样选变量、怎样缩小问题范围

按“命令 → 当前轨迹目标 → 实际反馈 → 负载 → 数据可信度”选，避免重复记录推导量。

| 看到的现象 | 优先缩小到哪里 |
|---|---|
| 目标先跳，反馈追赶 | 命令切换、目标设置、轨迹起点 |
| 目标平滑，反馈落后，力矩上升 | 负载、卡滞、参数、轨迹要求过高 |
| 反馈角度不变，年龄不断增加 | 通信链路；先别下结论是机械堵转 |
| 目标反馈吻合，实际姿态不对 | 零点、传动、机械安装、运动学模型 |
| Event 显示指令发完，反馈还没到 | 需要补到位判定，而不是把 finish 当成功 |

宇树角度是 rad、速度是 rad/s；DJI 角度是 degree，不能混用阈值。
正运动学算出的末端位置不是独立位置传感器，不能用于证明皮带没有滑动。
力矩是驱动反馈及本驱动换算值，不能直接当作外部接触力或精确载荷。

## 8. 先按这个顺序验证

1. 编译、看静止状态下有效帧计数与反馈年龄。
2. VOFA 看同一只电机目标/反馈，确认单位和通道。
3. Event Recorder 看一条 Start 和一条 CommandsSent。
4. 在安全条件下手动禁用，检查 Cancel，确认重新使能不会续跑旧轨迹。
5. 手动快照，学会在 Watch 展开日志。
6. 反馈超时告警先用主机测试或受控模拟验证；不要在承重运动中拔线、堵转或碰限位。
7. 最后才根据实测数据讨论到位容差、跟随误差、实际安全停止策略。

后续若要自动保护，应由主控确认故障处置、阈值和恢复流程，再接入输出通道。
本版不改点表、不自动回零、不自动改驱动参数、不写 Flash。
