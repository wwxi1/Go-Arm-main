# 两个安全诊断测试

测试1验证真实轨迹入口的几何不可达拦截；测试2验证正常动作完成后，位置误差超出10 mm时能否记录到位超时。两个测试都不引入新的物理运动目标。它们不是堵转或机械限位试验。

## 准备

机构停稳、可靠支撑并按原方式禁用；在允许重新建立软件零位的规定姿态下编译下载。重新进入调试Run，让Keil读取更新后的原路径 `ArmDiagnostics.scvd`。Event Recorder勾选Enable。

只新增一个Watch变量：`g_diag_test_request`。请求处理后自动归0；请求1、2只在 `Is_on=0`、无运行轨迹、两台宇树驱动对象都禁用时接受。不要只为了绕过检查直接修改驱动器的enable字段，要用原来的机构禁用流程。

## 测试1：不可达位置

1. 确认机构禁用，主控保持Run。
2. 把 `g_diag_test_request` 写成1。
3. 预期出现 `TestUnreachableTarget`，随后出现红色 `InvalidTarget`。机械臂不应启动，不应产生TrajectoryStart或XYArrivalSuccess。

代码生成 `(L1+L2+100, 0) = (912.92, 0) mm`，超过812.92 mm的最大几何臂展。通过禁用检查后，先确认这个固定点确实被 `Arm_Pos_Valid` 拒绝，再送入真实的 `Arm_Interpolation_Cart_Start`。入口第一条判断就触发拒绝，尚未执行反解、轨迹初始化或更新电机目标。如果前置条件不成立，记录 `TestRequestRefused` 并清掉请求，不会等以后突然执行。

这个结果只验证几何可达域和数值检查。可达圆环内的点仍可能撞障碍、关节限位或引起干涉，不能用“代码会拦截”作通用安全保证。

## 测试2：实际目标与检验目标相差50 mm

1. 机构仍禁用，写 `g_diag_test_request=2`。
2. 确认事件 `TestXYOffsetArmed`，表示仅为下一动作准备测试；此时不会自动使能或运动。
3. 用原操作使能，执行一个已验证的正常动作，例如准备姿态state1。
4. 让动作走完，并在CommandsSent后至少再等2 s，不要立即切下一个动作或禁用。
5. 预期事件顺序：

```
TestXYOffsetArmed       check_offset_x_mm=50
TrajectoryStart
CommandsSent
TestXYOffsetApplied     check_offset_x_mm=50
XYArrivalTimeout       error_mm_rounded=约50
```

实际电机目标、轨迹、反馈数据都保持真实值，仅 `xy_check.final_xy.x` 在本次验证中增加50 mm。因此正常到位时仍应落在原目标附近，而验证器看到的是约50 mm偏差；读数不一定正好50，因为还有实际跟随误差。通常仍在原目标附近且反馈新鲜、无驱动错误时才预计显示这一范围；断线/报错时可能显示-1。

新动作或禁用如果发生在等待期间，会得到 `XYArrivalAborted`，不是Timeout。动作若在指令发完前已被替换/取消，测试绑定随该动作取消，不顺延给后续动作。

## 恢复

偏移只使用一次；下一动作会按真实目标正常验证，预期恢复XYArrivalSuccess。测试2已准备但不想执行时，在机构禁用状态写 `g_diag_test_request=3`，看到TestCancelled即可。重启也会清除测试。不要通过修改正常动作表或直接写电机cmd位置做这两个诊断测试。

本地测试验证了请求门控、一次性偏移、取消、正常动作不继承偏移以及电机目标保持；其中依赖硬件的轨迹模块在主机测试中使用替身。真实轨迹入口已做代码检查和Keil集成构建，板上结果仍需按上面流程验证。
